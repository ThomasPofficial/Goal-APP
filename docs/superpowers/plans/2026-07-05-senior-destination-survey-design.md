## Problem Statement

Nivarro tracks where students plan to go after graduation (`intendedCollege`, `intendedMajor`,
`industry`) but has no automated pipeline to collect where they *actually* went. The destinations
map at `/school/destinations` shows intended colleges from profile fields — it doesn't reflect
real outcomes. The gap: no survey system, no LinkedIn monitoring, no annual email cadence.

The goal is a full alumni lifecycle tracking system:
1. Auto-enroll graduating seniors the year they graduate
2. Send a May survey every year until alumni opt out
3. Periodically scan LinkedIn URLs for unreported job/college changes (admin notification only — no auto-update)
4. Feed confirmed data into new `confirmedCollege`/`confirmedMajor` fields so the destinations map can show both layers

---

## What Makes This Cool

- Email arrives pre-filled with LinkedIn data — alumni click "Confirm" to submit without visiting a form
- The destinations map shows two layers: "intended" (current students) vs. "confirmed actual" (alumni who responded)
- School counselors get a live cohort outcomes view that updates year-round, not just in May
- Job changes flagged mid-year without waiting for the next May survey

---

## Constraints

- LinkedIn fetching via public page HTML. **For demo:** use a pre-tested public LinkedIn URL confirmed to be fetchable from a server. **For production:** requires Proxycurl API ($0.01/profile) — Node.js `fetch()` from Render IPs hits LinkedIn's bot detection reliably. Do not assume `fetch()` works at scale.
- Render hosting: cron jobs call protected API endpoints with `CRON_SECRET` header
- **Render cron must use Node.js, not curl** — project has documented SSL issues with curl on this environment. Use `node -e "fetch(...).then(...)"` or a script.
- Email via Resend (already integrated at `lib/resend.ts`)
- Claude AI for LinkedIn page parsing (already used at `/api/orgs/[id]/analyze-applicants`)
- Alumni who are inactive on Nivarro can still respond — magic link, no login required
- Long-running LinkedIn batch cannot run synchronously in a single HTTP request (Render's HTTP timeout is ~30s). Must use background worker or chunk the work.

---

## Premises

1. Survey accessible via magic link — no Nivarro login required
2. LinkedIn monitoring = fetch public profile pages, pass to Claude to extract career/education data. Changes detected → email admin only. Profile is NOT auto-updated — confirmation required.
3. Survey responses update new `confirmedCollege`, `confirmedMajor` fields and existing `industry`, `employer`, `jobTitle` fields. `intendedCollege`/`intendedMajor` are NOT overwritten — they preserve the student's original intent for historical comparison.
4. Scheduling via Render cron jobs using Node.js, calling protected API endpoints
5. Alumni pool = users where `isAlumni: true` OR `graduationYear < current year`. Current-year graduates (e.g., June 2026 class) are picked up the following May — they are NOT included in the May survey before they have graduated.
6. "To retirement" means: surveys sent annually until alumni opt out via `surveyOptOut: true`. No forced stopping condition — it's the alumni's choice to opt out.

## Data Model Changes

### New: `SurveyToken` model

```prisma
model SurveyToken {
  id          String    @id @default(cuid())
  userId      String
  token       String    @unique @default(cuid())
  year        Int
  sentAt      DateTime  @default(now())
  expiresAt   DateTime  // sentAt + 60 days; validated on GET and POST
  respondedAt DateTime?
  prefillData String?   // JSON: {college, major, industry, employer, jobTitle} extracted from LinkedIn

  user User @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@unique([userId, year])
  @@index([userId])
}
```

### New: `LinkedinScanEvent` model

```prisma
model LinkedinScanEvent {
  id         String   @id @default(cuid())
  userId     String
  scannedAt  DateTime @default(now())
  field      String   // "employer", "jobTitle", "college", etc.
  prevValue  String?
  newValue   String?
  notified   Boolean  @default(false)  // whether admin was emailed

  user User @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@index([userId])
  @@index([scannedAt])
}
```

## Architecture

### Survey Flow (May 1 annual)

```
Render Cron (May 1, 9am UTC)
  → Node.js script: node -e "fetch('https://app.nivarro.co/api/admin/survey/enqueue', ...)"
    → POST /api/admin/survey/enqueue  (Bearer CRON_SECRET)
      → Writes job to a simple queue table (or just logs the cohort IDs)
      → Returns 200 immediately (no timeout risk)

Background worker (Render Background Worker or long-running process)
  → Reads queue
  → Finds all alumni pool: (isAlumni OR graduationYear < currentYear) AND NOT surveyOptOut
  → Skips users with SurveyToken for current year (idempotent)
  → Processes sequentially with 2s delay between requests, 10s timeout per LinkedIn fetch:
      → If user has linkedinUrl AND NOT linkedinScanOptOut:
          → fetch() public LinkedIn page (10s timeout)
          → If fetch succeeds: Claude extracts {college, major, industry, employer, jobTitle}
          → Store as prefillData in SurveyToken
          → If fetch fails: prefillData = null (blank form fallback)
      → Create SurveyToken (token, year, expiresAt = sentAt + 60 days, prefillData)
      → Send Resend email
```

**Simplified alternative (if background worker is too complex for hackathon):**
Admin clicks "Send Survey" in dashboard → endpoint processes up to 50 alumni per call → admin clicks again if more. Cap per call = 50, timeout-safe at ~30s max.

### Survey Response Flow

```
Alumni receives email → clicks magic link
  → GET /survey/[token]  (Next.js page route, server component)
      → Server: find SurveyToken by token
      → Validate: token exists, expiresAt > now(), respondedAt = null
      → If token invalid/expired: show "This link has expired" page
      → If already responded (respondedAt set): show read-only "Your response is on file" page with current data
      → If valid: render form pre-populated with prefillData (or empty)

  → Alumni edits/confirms and submits form
  → POST /api/survey/[token]  (no auth)
      → Find token, re-validate (expiresAt > now())
      → If already responded: return 409 with "already submitted" message
      → Update Profile:
          confirmedCollege, confirmedMajor, industry, employer, jobTitle, linkedinUrl
      → Set SurveyToken.respondedAt = now()
      → Return success page

"Confirm" CTA (pre-filled email only):
  → Implemented as a standard HTML <form method="POST" action="/api/survey/[token]">
    with hidden inputs containing the prefillData values.
    This is the only email-client-compatible method — fetch() in emails is blocked.
  → On 200: server redirects to /survey/[token]?success=true (confirmation page)
  → On 409 (already responded): redirect to /survey/[token]?already=true
  → On any 4xx/5xx: redirect to /survey/[token]?error=true
    → Alumni lands on the full form with a human-readable error message
  → "Update my info" opens /survey/[token] page with the form pre-populated.

Opt-out flow:
  → Email includes "Unsubscribe" link pointing to /api/survey/[token]/optout
  → POST /api/survey/[token]/optout  (no auth, same token reused)
      → Validate token exists (expiry not checked — opt-out should always work)
      → Set Profile.surveyOptOut = true
      → Redirect to /survey/optout-confirmed (static confirmation page)
  → Alumni with surveyOptOut: true are excluded from all future survey batches
```

### LinkedIn Monitoring Flow (monthly — notify only, no auto-update)

```
Render Cron (1st of each month, 10am UTC)
  → Node.js: node -e "fetch('https://app.nivarro.co/api/admin/survey/linkedin-scan', ...)"
    → POST /api/admin/survey/linkedin-scan  (Bearer CRON_SECRET)
      → Accepts optional `limit` (default 5) and `offset` (default 0) query params
      → **Same timeout risk as survey batch.** 5 alumni × (2s delay + 10s fetch) ≈ 60s max — within Render's limit.
        For pools > 5: admin clicks "Scan LinkedIn" multiple times, or the cron calls with increasing offsets.
        Hackathon: cap at 5 per call. Post-demo: background worker same as survey enqueue.
      → Find alumni with linkedinUrl AND NOT linkedinScanOptOut, ordered by lastLinkedinScan ASC (oldest first)
      → Apply limit/offset
      → Process sequentially (2s delay, 10s timeout per request):
          → fetch() LinkedIn page
          → Claude: compare extracted data with current Profile fields
          → If ANY field changed (employer, jobTitle, confirmedCollege):
              → Create LinkedinScanEvent record (field, prevValue, newValue)
              → Send email to school admin:
                  "[Name]'s LinkedIn shows: employer Google → OpenAI"
              → Do NOT update Profile — admin or alumni must confirm
          → Update Profile.lastLinkedinScan = now()
```

## New API Routes

| Route | Method | Auth | Purpose |
|---|---|---|---|
| `/api/admin/survey/enqueue` | POST | CRON_SECRET or ADMIN/SCHOOL | Trigger May survey batch (returns immediately; worker processes async) |
| `/api/admin/survey/linkedin-scan` | POST | CRON_SECRET or ADMIN/SCHOOL | Trigger LinkedIn monitoring scan |
| `/api/admin/survey/status` | GET | ADMIN/SCHOOL | Survey stats: sent, responded, response rate, pending LinkedIn scans |
| `/api/survey/[token]` | POST | None | Submit survey response (public, magic link) |
| `/api/survey/[token]/optout` | POST | None | Opt out of future surveys; sets surveyOptOut: true (public, same token) |

Note: `GET /survey/[token]` is a **Next.js page route** (server component), not an API route. Token validation happens server-side in the page component. No separate `GET /api/survey/[token]` needed.

## School Dashboard: `/school/survey`

- **Stats strip**: X alumni in pool · X surveys sent this year · X responded (Y% rate) · X pending
- **"Send Survey Now"** button — manual trigger (calls `/api/admin/survey/enqueue`)
- **"Scan LinkedIn Now"** button — manual trigger (calls `/api/admin/survey/linkedin-scan`)
- **Response table**: alumni name · graduation year · last survey sent · responded? · last LinkedIn scan
- **Detected changes log**: pulls from `LinkedinScanEvent` table — timestamp · alumni name · field · prev → new · "confirmed?" status

## Claude Prompt for LinkedIn Parsing

```
You are extracting career and education data from a LinkedIn public profile HTML page.
Extract these fields if present:
- college: the most recent college/university attended
- major: field of study at that college
- industry: the general industry (e.g., "Software", "Finance", "Healthcare")
- employer: current employer company name
- jobTitle: current job title

Return JSON only. If a field is not found, return null for that field.
Example: {"college":"MIT","major":"Computer Science","industry":"Software","employer":"Google","jobTitle":"Software Engineer"}
```

## LinkedIn Fetching Strategy

In order of reliability:

1. **For demo**: Identify one specific alumni LinkedIn URL confirmed to be fetchable from a server IP. Use it to demonstrate the pre-filled flow.
2. **Node.js `fetch()` with browser-like headers**: Works intermittently for public profiles. Add `User-Agent`, `Accept-Language`, `Accept` headers matching a real browser.
3. **If blocked (HTTP 999, redirect to login)**: prefillData = null, send blank survey. Log the failure.
4. **For production**: Budget Proxycurl from day one ($0.01/profile). LinkedIn blocking from server IPs is near-certain at any meaningful scale.

## Approaches Considered

### Approach A: Survey-only (Minimal Viable)
- Survey email + magic link form, no LinkedIn
- Effort: S (1 day) | Risk: Low

### Approach B: Survey + AI LinkedIn prefill
- Survey prefilled from LinkedIn before email sends
- Effort: M (2-3 days) | Risk: Medium

### Approach C: Full automated pipeline (chosen)
- Annual May survey + periodic LinkedIn monitoring (notify-only) + admin dashboard
- Effort: XL (1 week) | Risk: High
- Build in phases so each day is demo-able (see Next Steps)

---

## Recommended Approach

**Approach C — Full automated pipeline**, built in day-by-day phases:

- **Day 1**: Schema migration. `/api/admin/survey/enqueue` (processes synchronously up to 50 alumni, good enough for demo). `/survey/[token]` page + POST handler. "Send Survey" button in `/school/survey`. Blank survey form working end-to-end.
- **Day 2**: Resend email templates (blank + pre-filled). LinkedIn fetch + Claude parse. Pre-fill logic wired into enqueue. "Confirm" one-click CTA in email.
- **Day 3**: `/api/admin/survey/linkedin-scan`. `LinkedinScanEvent` records. Admin notification email. LinkedIn changes log on `/school/survey` dashboard.
- **Day 4**: Render cron job configuration. End-to-end test with real alumni email and pre-tested LinkedIn URL. Opt-out flow. Response stats strip.

If Day 3–4 run short, the Day 1–2 build is already a compelling demo.

## Open Questions

1. **Background worker vs. chunked endpoint**: For the hackathon, the 50-alumni-per-call approach is fine. For production, a Render Background Worker is the right architecture. Revisit post-demo.
2. **Proxycurl budget**: At $0.01/profile × annual scans × monthly monitoring, budget depends on alumni pool size. For a school with 200 alumni, $2/month annual survey + $2/month monitoring = $4/month. Probably acceptable.
3. **Opt-out link in email**: The unsubscribe link needs a separate token or use the survey token itself with a `?action=optout` param. Specify before Day 1.
4. **Admin notification frequency**: Current design sends one email per detected LinkedIn change. For schools with large alumni pools, a daily digest may be less noisy. Defer to v2.
5. **Destinations map update**: The map currently reads `intendedCollege`. After this ships, update it to prefer `confirmedCollege` for alumni and `intendedCollege` for current students. This is a one-line query change — add to Day 4.

## Success Criteria

- School admin clicks "Send Survey" → emails hit alumni inboxes within 5 minutes
- Alumni without LinkedIn URL receive blank form, complete it, `confirmedCollege` and `confirmedMajor` update
- Alumni with LinkedIn URL receive pre-filled form, click "Confirm," Profile updates without visiting the form
- Destinations map shows `confirmedCollege` for alumni who responded, `intendedCollege` for current students
- Monthly LinkedIn scan detects a real job change and emails school admin with structured before/after
- Render cron fires May 1 without manual intervention
- Alumni with `surveyOptOut: true` do not receive surveys
